# Design: ai-english-coach

## Context

现有产品是「纯静态前端（vanilla JS）+ 本地 Python 转发」的英语听力训练器：117 词、听写句、连读弱读规则写死，AI 仅在「说英语」页当陪聊，数据存 localStorage，AI 无法记住用户。本变更将其重做为 AI 驱动的英语交流教练，目标用户在 3~6 个月内从「开会能听懂大意但不敢开口」到「能独立应付工作会议里的听说」，每天 1 小时，由 AI 编排。约束：不考虑离线（纯 AI 驱动）；多场景并行训练、互不影响；Web 应用桌面优先。

现有内容资产（117 词、听写句、15 条连读弱读规则、20 个言语功能、场景库）保留为 AI 的冷启动种子与难度标定基准。

## Goals / Non-Goals

**Goals:**
- 建立「AI 教练」完整闭环：评估 → 训练 → 实战 → 复盘 → 明日计划，每步产物流回画像。
- 用户画像分轨（按场景维度），支撑多场景并行训练互不影响。
- 首次测验真正发掘短板（分层探测 + 反应时间 + 自适应）。
- 每天 1 小时由 AI 动态编排（4 块结构）。
- 北极星指标落地：场景成功率（「办成的事」数量 + 言语功能三场合毕业）。

**Non-Goals:**
- 不做多租户 SaaS（当前单用户自托管形态，但数据模型预留 user_id 扩展点）。
- 不做移动端原生 App（Web 优先，桌面端可后续套壳）。
- 不追求「纠正发音」的精细音素级反馈（那是另一个产品，本产品聚焦「能交流」）。
- 不做社交/排行榜/打卡等游戏化机制（第一版聚焦教练价值本身）。

## Decisions

### D1：后端用 Python (FastAPI)
- **选择**：FastAPI + uvicorn，承担画像存储、LLM 编排、流式对话、ASR 调用、种子数据管理。
- **理由**：现有 `server.py` 已是 Python；Whisper ASR、LLM SDK、流式 SSE 在 Python 生态最成熟。
- **替代**：Node/TypeScript 可全栈统一，但 ASR/LLM 编排生态弱于 Python，且无现有资产复用。

### D2：数据存储用 SQLite（预留 PostgreSQL 迁移）
- **选择**：SQLite 存结构化数据（用户、训练记录、场景战绩），画像的复杂维度用 JSON 字段存半结构数据。
- **理由**：单用户自托管，数据量小，零运维；JSON 字段适配画像维度的灵活演化。
- **替代**：PostgreSQL 从一开始引入，增加部署负担；第一版不需要。

### D3：前端用 React + Vite（SPA）
- **选择**：React + TypeScript + Vite，SPA 形态，通过 API 与 FastAPI 通信，录音用 MediaRecorder API，实时对话用 SSE。
- **理由**：训练 UI 复杂度高（多块编排、录音、流式对话、自适应出题），vanilla JS 已难以维护；SPA 无需 SSR。
- **替代**：保持 vanilla JS 复用现有代码——但现有 UI 是围绕固定题库设计的，重做成本相当，且长期维护差。

### D4：多轨道画像数据模型（domain 分片）
- **选择**：画像以 `domain`（场景，如 work/travel/interview）为一级分片键，每个 domain 下独立存听力盲区、词汇掌握度、表达回避、场景战绩、错误史。另设一个全局层存「跨场景通用短板」（如基础连读）。
- **理由**：直接落地「多场景并行训练互不影响」；同时全局层避免「换场景就全忘了」的碎片化。
- **替代**：单一线性画像——无法支持多场景并行，违背已确认需求。

### D5：LLM 编排为多角色管线，成本分层
- **选择**：后端内多个 LLM 角色 prompt：评估器（首次测验）、诊断器（每日复盘）、内容生成器、场景演员（群聊）、教练报告器。调用成本分两层：高频训练生成用轻量 prompt + 短输出；复盘/诊断/报告用深度 prompt。
- **理由**：token 成本与延迟是「AI 驱动」的主要风险，分层控制是可持续运行的前提。
- **替代**：所有环节都深度调用——成本失控且高频环节延迟高。

### D6：语音方案
- **选择**：TTS 用云端高质量语音（OpenAI TTS / Azure / Edge-TTS），对话场景流式；ASR 用 Whisper 系（优先本地 faster-whisper，可切云端 API）做口语转写与评估。
- **理由**：口语产出评估依赖可靠 ASR；TTS 决定「真实语流变形」的还原度（弱读/连读），云端质量最高。
- **替代**：浏览器 Web Speech API TTS——质量不足以还原真实语流变形，违背产品核心方法论。

### D7：种子数据抽取与难度标定
- **选择**：把 `data.js` 的 CARDS/SENTENCES/REDUCTIONS/SKILLS/SCENARIOS 抽取为后端可读的种子数据文件（JSON/YAML），并补难度标定字段，作为冷启动与生成参照。
- **理由**：内容资产是已验证的高质量语料，直接丢弃浪费；带难度标定后成为自适应出题的底座。
- **替代**：完全从零生成——冷启动阶段 AI 无画像可依，质量不稳定。

### D8：首次测验自适应算法
- **选择**：测验采用「能力边界二分定位」+「短板定向追加」：听力题按难度档位二分逼近用户边界；检测到某类连续出错则定向追加该类题目；全程记录反应时间。
- **理由**：固定试卷无法「发掘真实短板」，自适应是 AI 测验的本质优势。
- **替代**：固定题量固定顺序——违背已确认的「真的发掘短板」要求。

## Risks / Trade-offs

- [画像准确性：AI 判断错短板会带偏整条训练线] → 首次测验必须请用户确认（spec 已要求），并支持用户纠正；画像条目带置信度，低置信度条目降低对训练的权重。
- [生成内容质量忽难忽易] → 难度标定字段 + 用户反馈（答对/答错）动态校准难度；种子语料作为风格与难度基准锚点。
- [Token 成本失控] → D5 分层调用；训练生成设输出长度上限；缓存近期生成素材避免重复生成。
- [每天 1 小时用户坚持难] → AI 动态编排（块时长随状态调整）+ 教练报告给正向反馈；这是产品留存的核心风险，需在阶段 4 通过报告强化动机。
- [多轨道导致画像碎片化] → D4 的全局层共享跨场景通用短板，避免「换场景就全忘」。
- [流式对话延迟影响体验] → SSE 流式 + 轻量场景演员 prompt；首 token 延迟设目标值。

## Migration Plan

全新产品，无历史数据迁移。现有代码退役，内容资产抽取为种子数据。部署形态：`pip install` 依赖后 `uvicorn` 启动后端，前端 Vite 构建后由后端静态托管。回滚策略：变更在独立 change 目录与 feature 分支内完成，未归档前可整体放弃。

## Open Questions

- ASR 具体选型：本地 faster-whisper vs 云端 API（成本与延迟权衡），首版建议云端 API 起步、本地留接口。
- 是否需登录鉴权：单用户自托管暂不需要，但 API 层预留 `user_id` 以便将来多用户。
- 种子数据的难度标定字段由谁维护：首版由 AI 离线批量标定一次，后续由用户反馈动态校准。
